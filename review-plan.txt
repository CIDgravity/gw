Review plan

What is already done in code on this branch:
- WAL read/write concurrency is fixed with a regression test.
- Replica count 0 is rejected at config load.
- kuri no longer auto-generates a wallet on startup; gwcfg remains the wallet creation path.
- gwcfg only issues one explicit /fil request during setup.
- Default LocalWeb staging path is now `<RIBS_DATA>/cardata`.
- UI external links are fixed (`app.cidgravity.com`, `filecoin.tools/search?q=`).
- Deal loop state is now exposed in the UI (`running`, `next check`, `last duration`, `backoff`, `last error`).
- The deal check loop now applies bounded exponential backoff after loop-level failures.
- Startup DB initialization now retries for both SQL and YCQL instead of failing immediately on transient startup races.
- Docker compose is hardened a bit: safer `init && daemon`, restart policies, 443->8443 mapping, metrics/UI bound to localhost.
- Built-in LocalWeb no longer uses the hardcoded JWT; it now serves capability URLs via the randomized staged CAR filename.
- Wallet / faucet RPC visibility handling is more tolerant of transient `actor not found` / `execution reverted` states.
- Multipart handling is tightened a bit: upload routing now rejects non-active uploads in the frontend, and S3 handlers reject out-of-range part numbers / markers.

Concrete follow-up plan with no open questions:

1. Multipart follow-up hardening
- Keep multipart parts out of normal object listings even after crashes.
- Preferred implementation: stop storing multipart parts in the normal object namespace, or explicitly filter temporary `expires_at` entries from user-facing list paths while preserving an internal path for ListParts.
- Add tests for:
  - aborted upload -> `ListParts` is not accessible
  - completed upload -> `ListParts` is not accessible
  - temporary multipart parts never appear in normal bucket listings
  - crash leftover parts are removed by cleanup and never leak through object list APIs
  - part number cap stays bounded at 10000

2. Dealmaking / provider pressure
- Current improvement is loop-level backoff and visibility.
- Next step if DB/SP pressure still shows up: add provider-specific cooldowns keyed by provider + failure/rejection reason so the selector does not revisit the same busy/unavailable SPs every global loop.
- Surface provider cooldown / next attempt time in provider diagnostics if that lands.

3. LocalWeb support model
- Support exactly two deployment modes:
  - built-in autocert mode: `EXTERNAL_LOCALWEB_URL=https://host`, public DNS points at the node, compose maps `443:8443`
  - reverse-proxy mode: `EXTERNAL_LOCALWEB_SERVER_TLS=false`, gateway listens internally on `8443`, nginx/caddy/ingress owns 443 and forwards to the gateway
- In both modes, add a pre-deal HEAD probe against the staged CAR URL before proposing the deal.
- If neither mode is configured correctly, fail fast instead of silently limping along.

4. Compose / deployment hardening
- Keep metrics and RIBSWeb localhost-bound by default.
- Keep restart policies enabled.
- Keep startup retry in-process; do not rely on `depends_on` for restart sequencing.
- Add a short production checklist to docs:
  - wallet secret mounted
  - S3 auth enabled
  - LocalWeb mode selected explicitly
  - 443 reachable if autocert mode is used
  - metrics/UI not publicly exposed by default

5. CAR download auth model
- JWT is removed.
- The intended model is now capability URLs backed by randomized staged CAR filenames.
- If stronger auth is needed later, use a DB-backed opaque token or one-time URL, not a hardcoded shared JWT secret.

6. RPC error handling
- Treat wallet visibility / datacap lookups as eventually consistent during bootstrap.
- Keep returning partial wallet state rather than failing the whole RPC when the chain has not indexed the wallet yet.

7. UI polish follow-up
- Keep the explicit selected-state styling for binary actions.
- If more ambiguous binary controls exist, convert them to the same active/inactive segmented pattern rather than relying on color alone.

Operational recommendation
- Treat docker-compose as a hardened single-node deployment helper, not as a generic drop-in internet-facing default.
- For multi-node or public deployments, prefer a real orchestrator / ingress setup and make the LocalWeb mode explicit.
